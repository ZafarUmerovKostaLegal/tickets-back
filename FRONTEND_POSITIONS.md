# Фронт: справочник должностей (positions)

Инструкция для фронтенда по новому справочнику должностей. По должностям дальше
будем делить доступы в time tracking. Сейчас задача фронта — брать список
должностей из бэкенда (а не хардкодить) и использовать его при назначении
должности пользователю.

---

## 1. Новый эндпоинт — список должностей

```
GET /api/v1/positions
```

- Требует авторизацию (Bearer-токен, как и остальные `/api/v1/...`).
- Доступен любому авторизованному пользователю.

### Ответ (200)

```json
{
  "positions": [
    "Business Development Manager",
    "Contracts and BD Assistant",
    "Accountant",
    "Office Manager"
  ]
}
```

Порядок элементов — канонический (как отдаёт бэкенд), используйте его как есть
для выпадающего списка. Список может пополняться на бэкенде — **не хардкодьте**
значения на фронте, всегда берите из этого эндпоинта.

---

## 2. Где использовать

Должность хранится в поле `position` пользователя. Оно задаётся/меняется через
существующие эндпоинты управления пользователями:

- Создание пользователя: `POST /api/v1/users` — поле `position`.
- Смена должности у существующего пользователя: текущий эндпоинт смены должности
  (поле `position`), который вы уже используете в карточке пользователя.

Что сделать в UI:

1. На экранах, где назначается/редактируется должность пользователя, заменить
   текстовое поле (или старый хардкод-список) на **выпадающий список**,
   наполненный из `GET /api/v1/positions`.
2. Значение, выбранное в списке, отправлять как `position` без изменений
   (строкой, точно как пришло из `positions`).
3. Список загружать один раз при открытии формы (можно кэшировать на сессию).

---

## 3. Важные нюансы

- **Поле `position` на бэкенде — свободный текст.** Справочник задаёт
  рекомендованный набор значений, но технически принимается любая строка.
  Поэтому у уже существующих пользователей может быть должность, которой нет в
  списке (старые данные). Обработайте этот случай:
  - если текущее значение `position` пользователя не входит в список из
    `GET /api/v1/positions`, всё равно покажите его в выпадающем списке как
    выбранный пункт (например, добавив его в начало как «текущее значение»),
    чтобы при сохранении форма случайно не затёрла должность.
- **Регистр и пробелы.** Отправляйте значение ровно так, как оно пришло из
  эндпоинта. Бэкенд умеет приводить к каноническому написанию, но лишние
  расхождения по регистру лучше не плодить.
- **Роль (`role`) и должность (`position`) — это разные поля.**
  - `role` — системная RBAC-роль (Главный администратор, Администратор, Партнер,
    IT отдел, Офис менеджер, Сотрудник) — управляет доступом уже сейчас.
  - `position` — должность из этого справочника — по ней будем делить доступы в
    time tracking позже.
  Не путайте их в UI: это два независимых селектора.

---

## 4. Что НЕ нужно делать сейчас

- Не реализуйте на фронте логику «какая должность что видит/может в time
  tracking» — правила доступа по должностям будут добавлены на бэкенде отдельным
  шагом и приедут через стандартные проверки прав/ответы API. Фронту нужно лишь
  корректно хранить и показывать должность.

---

- [ ] Заменить ввод должности на выпадающий список из ответа эндпоинта.
- [ ] Сохранять выбранное значение в поле `position` при создании/редактировании

- [ ] Корректно показывать «нестандартную» текущую должность (которой нет в
