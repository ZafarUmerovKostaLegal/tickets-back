# Учёт времени (Time Tracking) — инструкция для фронтенда

Все запросы ниже идут через **gateway** с префиксом:

`https://<хост>/api/v1/time-tracking`

Заголовок: **`Authorization: Bearer <JWT>`** (тот же, что для остального приложения; для операций изменения нужны соответствующие роли TT в gateway).

Тела запросов: **JSON**. Имена полей в примерах даны в **camelCase**, как в API (алиасы Pydantic).

---

## 1. Создание проекта и участники со ставками

**`POST /api/v1/time-tracking/clients/{clientId}/projects`**

### 1.0. Текущий поток в SPA (`tickets-front`)

Ниже — как сейчас устроено создание проекта в клиенте (может отличаться от «идеального» контракта с **`initialProjectAccessMembers`**, см. п. 1.1).

1. **Создание проекта** — **`POST .../clients/{clientId}/projects`** с полями формы проекта и списком **`initialTimeTrackingUserAuthIds`**. Чтобы ставки из формы **учлись в этом же запросе** и не сработала проверка «нет billable в валюте проекта», в тело нужно добавить **`initialTimeTrackingUserBillableHourlyAmounts`** — массив **той же длины** и **в том же порядке**, что и id (см. п. 1.2). Альтернатива — **`initialProjectAccessMembers`** (п. 1.1). Если отправить **только** id без ставок в теле **`POST`**, бэкенд выдаёт доступ сразу при создании и вернёт **`400`**, если у пользователя ещё нет глобальной ставки в валюте проекта.

2. **Задачи** — в ответе **`POST`** дефолтный набор задач **не** возвращается; бэкенд после создания проекта сам добавляет типовые задачи (сид). В форме пользователь может **сузить** набор (модальное окно с переключателями по списку, совпадающему с серверным сидом). После **`POST`** клиент для **каждого выбранного** имени задачи вызывает **`POST .../clients/{clientId}/projects/{projectId}/tasks`** с нужными полями (`name`, `billableByDefault` и т.д. по схеме). Если имя уже есть у проекта, поведение зависит от валидации TT (дубликат по имени / ошибка — смотрите ответ API).

3. **Участники и доступ** — после успешного **`POST`** проекта, если включён режим **почасовой ставки сотрудника** (`billableRateType = person_billable_rate`), клиент **перед** выдачей доступа к проекту:
   - для каждого участника с заполненной суммой в форме загружает billable-ставки: **`GET /api/v1/time-tracking/users/{authUserId}/hourly-rates?rateKind=billable`**;
   - проверяет, есть ли **активная** (по датам `validFrom` / `validTo`) billable-ставка в **валюте проекта** (`currency` из проекта);
   - если такой ставки **нет** — создаёт её: **`POST /api/v1/time-tracking/users/{authUserId}/hourly-rates`** с `rateKind: "billable"`, суммой из формы, **`currency`** = валюта проекта и при необходимости привязкой к проекту (`projectId` в теле — как в схеме gateway/TT);
   - затем для каждого участника вызывает **`PUT /api/v1/time-tracking/users/{authUserId}/project-access`**, добавляя `projectId` в список.

Так уменьшается риск **`400`** «нет billable-ставки в валюте проекта» при назначении доступа, если пользователь ввёл сумму в форме, но глобальной ставки в USD (и т.п.) ещё не было.

### 1.1. Рекомендуемый способ: участники + billable-ставка по проекту

Чтобы не требовать заранее глобальную почасовую ставку пользователя в профиле, передавайте участников списком **`initialProjectAccessMembers`**. Для каждого участника можно задать **`billableHourlyAmount`** — она сохраняется **с привязкой к проекту** (`applies_to_project_id` в БД): при смене глобальных ставок позже суммы по **старым** записям времени на этом проекте по-прежнему считаются от ставки, зафиксированной для проекта.

Если **`initialProjectAccessMembers` непустой**, состав команды при создании берётся **только из этого списка** (поле **`initialTimeTrackingUserAuthIds`** для состава можно не заполнять).

Пример:

```json
{
  "name": "Проект для тестов",
  "projectType": "time_and_materials",
  "currency": "USD",
  "reportVisibility": "managers_only",
  "initialProjectAccessMembers": [
    { "authUserId": 101, "billableHourlyAmount": 100 },
    { "authUserId": 102, "billableHourlyAmount": 100 }
  ],
  "accessGrantedByAuthUserId": 1
}
```

- **`billableHourlyAmount`**: неотрицательное число; **`0`** или отсутствие поля — для этого пользователя действует прежняя проверка: должна быть подходящая **глобальная** billable-ставка в валюте проекта на текущую дату.
- Валюта ставки совпадает с **`currency`** проекта.

### 1.2. Параллельные массивы: id и ставки (удобно, если уже шлёте `initialTimeTrackingUserAuthIds`)

Добавьте второй массив **`initialTimeTrackingUserBillableHourlyAmounts`** — для каждого индекса **`i`** значение — это **billable за час** участника **`initialTimeTrackingUserAuthIds[i]`** на **этом** проекте (сохраняется с привязкой к проекту). Длина массивов должна **совпадать**. Вместо числа можно передать **`null`**, если для этого участника достаточно уже существующей глобальной ставки в валюте проекта.

Пример (как на вашем скриншоте, но **со ставками в JSON**):

```json
{
  "name": "Тестовый проект",
  "currency": "USD",
  "projectType": "time_and_materials",
  "billableRateType": "person_billable_rate",
  "initialTimeTrackingUserAuthIds": [1, 11],
  "initialTimeTrackingUserBillableHourlyAmounts": [100, 100]
}
```

Нельзя одновременно заполнять **`initialTimeTrackingUserBillableHourlyAmounts`** и **`initialProjectAccessMembers`** — выберите один способ.

### 1.3. Только id пользователей (без ставок в `POST`)

```json
{
  "name": "Проект",
  "initialTimeTrackingUserAuthIds": [101, 102]
}
```

Здесь в теле создания **нет** сумм: при выдаче доступа ожидается готовая billable-ставка в валюте проекта, иначе **`400`**.

**Обход без изменения `POST`:** шаг из п. **1.0** — **`POST .../hourly-rates`** и затем **`PUT .../project-access`** **после** создания проекта **без** участников в первом запросе; либо передавать ставки в **`POST`** как в п. **1.1** или **1.2**.

### 1.4. Режим «ставка по проекту» на всех

Если у проекта заданы **`billableRateType`** / **`projectBillableRateAmount`** так, что включён общий режим ставки по проекту, пер-сотруднические суммы из **`initialProjectAccessMembers`** для billable **не** подставляются отдельно — после выдачи доступа ставки участникам синхронизируются с полями проекта.

## 2. Задачи проекта (в т.ч. дефолтные после создания)

Дефолтные задачи **не** приходят в теле ответа **`POST .../projects`**. После создания их можно получить отдельным запросом по **`projectId`** из ответа создания.

**`GET /api/v1/time-tracking/clients/{clientId}/projects/{projectId}/tasks`**

Используйте **`id`** созданного проекта из ответа **`POST`** как **`projectId`**. Старый путь вида **`/clients/{clientId}/tasks`** для списка задач проекта **не используйте**.

Дополнительные задачи (не из дефолтного сида) создаются через **`POST .../projects/{projectId}/tasks`**. В SPA при создании проекта выбор «какие дефолтные задачи оставить» реализован поверх заранее известного списка имён (как в сиде TT); фактический список после создания всё равно стоит **подтвердить** **`GET .../tasks`**, если нужна синхронизация с сервером.

## 3. Доступ к проектам пользователю и ставки по проектам

**`PUT /api/v1/time-tracking/users/{authUserId}/project-access`**

Тело:

```json
{
  "projectIds": ["uuid-проекта-1", "uuid-проекта-2"],
  "projectBillableHourlyAmountsByProjectId": {
    "uuid-проекта-1": 100
  }
}
```

- **`projectBillableHourlyAmountsByProjectId`** — необязательно. Ключ — **id проекта** (строка), значение — **billable за час** для этого пользователя **на этом проекте** (фиксируется как ставка с привязкой к проекту).
- Имеет смысл для проектов **без** единой ставки «по проекту» на всех. Для режима общей ставки по проекту по-прежнему действует синхронизация с настройками проекта.
- Запрос выполняйте **до** логики, которая ожидает уже выданный доступ; upsert ставок на бэкенде делается в рамках этого же запроса перед проверками доступа.

Поле **`grantedByAuthUserId`** в теле при вызове **через gateway** обычно подставляет сам gateway из текущего пользователя; уточните у бэка, если вызываете TT напрямую.

## 4. Типичные ошибки

| Симптом | Что проверить |
|--------|----------------|
| **400**: нет billable-ставки в валюте проекта | В **`POST .../projects`** добавить **`initialTimeTrackingUserBillableHourlyAmounts`** (п. 1.2) или **`initialProjectAccessMembers`** (п. 1.1); либо не слать участников в **`POST`** и выдать доступ после **`POST .../hourly-rates`**. При **`PUT project-access`** — **`projectBillableHourlyAmountsByProjectId`**. |
| Пустой список задач | URL **`.../projects/{projectId}/tasks`**, корректные **`clientId`** и **`projectId`**, работоспособность сервиса TT и миграций БД. |
| **503** при операциях TT | Недоступен сервис time-tracking или auth; текст ответа часто содержит причину. |

---

## 5. Сериализация

- Деньги/ставки в JSON — числа; дробная часть допустима.
- Даты в теле проекта: **`startDate`**, **`endDate`** — строки **`YYYY-MM-DD`** или `null`, в зависимости от того, как шлёт ваш клиент (см. OpenAPI/Swagger gateway).

Для полного списка полей тела создания/патча проекта смотрите схемы **`TimeManagerClientProjectCreateBody`** / **`TimeManagerClientProjectPatchBody`** в репозитории (`gateway/presentation/schemas/time_manager_client_projects.py` и сервис TT `time_tracking/presentation/schemas.py`).
