# Разблокировка редактирования времени (24 ч) — инструкция для фронтенда

## Назначение

Менеджер учёта времени или администратор организации может **временно снять блокировку** внесения/изменения часов за **конкретный календарный день** для **конкретного сотрудника**. После выдачи разблокировки **24 часа** (от момента успешного запроса на бэкенде) этот день для этого пользователя считается открытым для записей, даже если обычные правила (сдача недели, дедлайн и т.п.) день бы закрывали.

Повторный запрос на ту же пару **пользователь + дата** **продлевает** окно ещё на **24 часа** от нового запроса (перезаписывается время истечения и кто выдал).

Отдельного API «посмотреть активные разблокировки» нет: после успешного `POST` можно показать пользователю `expiresAt` из ответа.

---

## Эндпоинты (через gateway)

Используйте тот префикс, который уже принят в клиенте для учёта времени.

### Вариант A — префикс time-tracking

`POST /api/v1/time-tracking/users/{authUserId}/time-entry-edit-unlock`

### Вариант B — алиас под users

`POST /api/v1/users/{authUserId}/time-entry-edit-unlock`

Поведение и права одинаковые; отличается только путь.

**Параметр пути:** `authUserId` — целочисленный id пользователя в auth (тот же, что для `time-entries`).

**Авторизация:** обычные заголовки сессии/API к gateway, как для остальных запросов учёта времени.

---

## Тело запроса

JSON. Поля поддерживаются в **camelCase** (предпочтительно для фронта) и **snake_case**.

| Поле        | Тип    | Обязательно | Описание                          |
|------------|--------|-------------|-----------------------------------|
| `workDate` | string | да          | Дата рабочего дня, формат `YYYY-MM-DD` |

Пример:

```json
{
  "workDate": "2026-04-21"
}
```

---

## Ответ при успехе (200)

Тело JSON (типично camelCase в сериализации FastAPI):

| Поле                 | Тип     | Описание                                      |
|----------------------|---------|-----------------------------------------------|
| `authUserId`         | number  | Кому выдана разблокировка                     |
| `workDate`           | string  | Дата (`YYYY-MM-DD`)                           |
| `grantedByAuthUserId`| number  | Кто выдал (текущий пользователь при успехе)  |
| `expiresAt`          | string  | ISO-8601, до какого момента активна разблокировка |
| `createdAt`          | string  | ISO-8601, когда создана/обновлена запись       |

Имеет смысл показать менеджеру текст вроде: «Сотрудник может внести правки до …» по `expiresAt`.

---

## Ошибки (кратко)

- **403** — недостаточно прав или попытка выдать разблокировку «самому себе» без роли администратора/партнёра/гл. администратора (обычный сотрудник и менеджер TT не могут вызвать метод с `authUserId`, равным своему id, если у вызывающего нет org-manage роли из списка ниже).
- **403** — менеджер учёта времени пытается выдать разблокировку сотруднику **вне peer-scope** (нет общих проектов доступа согласно правилам TT).
- Прочие **4xx/5xx** — как у остальных проксируемых методов (деталь в теле ответа).

### Кто может выдавать разблокировку

- Организационные роли с полными правами на чужие записи времени: **Главный администратор**, **Администратор**, **Партнёр** — могут выдать любому `authUserId` (включая повторное продление), в рамках общей логики записи времени.
- **Менеджер учёта времени** (роль `manager` в сервисе TT): только сотрудникам из своего scope (**общие проекты доступа**), и **не может** выдать разблокировку **себе**, если у него нет org-manage роли выше.

Точные тексты ошибок приходят с бэкенда в `detail` — их можно показывать как есть или маппить на UI.

---

## Поведение для сотрудника после выдачи

Пока `expiresAt` в будущем, проверки «день заблокирован для редактирования» для пары `(authUserId, workDate)` **не блокируют** ввод. После истечения срока действуют обыные правила блокировки.

Фронту не обязательно хранить разблокировку локально: достаточно успешного создания/изменения записей времени в этом окне; при необходимости UX можно подсвечивать дедлайн по последнему известному `expiresAt` из ответа `POST`.

---

## Связанные методы

Создание и изменение записей по-прежнему через существующие маршруты `time-entries` для того же `authUserId`. Разблокировка только снимает **блок по дате** для этого пользователя; остальные проверки (проекты, валидации полей) не отменяются.
